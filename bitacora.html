📖 BITÁCORA DE DESARROLLO

Registro del proceso de desarrollo, decisiones técnicas y desafíos encontrados durante la construcción del sitio web DEVOPOLY

🎲 PLANIFICACIÓN Y CONCEPTO

Semana 1 Concepto

Selección de temática: Monopoly como eje central

Decisión

El equipo adoptó la temática del juego de mesa Monopoly como eje conceptual principal del proyecto web. Este enfoque permitiría diferenciar el sitio de propuestas convencionales.

Justificación

La temática Monopoly ofrece una metáfora efectiva para presentar a los integrantes: cada persona como una "propiedad", las habilidades representadas como "rentas", y los perfiles estructurados como "títulos de propiedad". Esta estructura proporciona coherencia visual y conceptual a través de toda la experiencia del usuario.

Desafío identificado

La comunicación inicial de la propuesta conceptual requirió múltiples iteraciones para que todos los integrantes comprendieran completamente cómo se implementaría la temática en el código y la estructura HTML.

Resolución

Se desarrolló una propuesta documentada que detallaba la estructura completa: tablero como portada, fichas como enlaces a perfiles, tarjetas de propiedad como presentación de datos individuales, y un sistema de navegación dual que permitiera explorar tanto a través del juego como mediante menú tradicional. Esta documentación facilitó la alineación del equipo.

Semana 1 Decisión

Enfoque de desarrollo: estructura primero, detalles después

Decisión

Se estableció una estrategia de desarrollo modular en fases: primero asegurar la estructura HTML correcta y funcional, luego implementar estilos CSS y comportamientos JavaScript, y finalmente ajustar detalles visuales y contenido personalizado.

Justificación

Este enfoque reduce la probabilidad de conflictos durante la integración de trabajo colaborativo. Permite que cada integrante trabaje en su perfil con un esquema base consistente, sin depender de que otros completen sus tareas estéticas primero.

Desafío identificado

Mantener consistencia en la estructura mientras se permite trabajo paralelo. Algunos integrantes presentaban versiones con datos incompletos o placeholders temporales.

Resolución

Se definieron patrones HTML comunes para todos los perfiles (estructura de tarjeta, clases CSS, disposición de elementos). Cada integrante completa su perfil siguiendo este patrón, incluyendo placeholders cuando datos específicos aún no están disponibles. Los detalles estéticos se unifican en una fase posterior.

Semana 1 Decisión

Organización en Git: ramas de trabajo independientes

Decisión

Cada integrante del equipo trabaja en una rama independiente: perfil-brian, perfil-flavia, pedro, perfil-ludmila. Se creó además una rama dedicada a la bitácora de desarrollo.

Justificación

Las ramas independientes evitan conflictos directos en la rama principal (main). Cada integrante es responsable de su rama y puede trabajar sin interferencias. Facilita la revisión de cambios antes de hacer merge a main.

Desafío identificado

Algunos integrantes presentaron complejidad en la gestión de Git, particularmente en operaciones de merge, resolución de conflictos y sincronización con la rama principal.

Resolución

Se estableció comunicación directa entre integrantes para notificar cambios. Un integrante con mayor experiencia en Git se responsabilizó de revisar y ejecutar los merges hacia main, resolviendo conflictos cuando fuera necesario. Se agregaron validaciones en JavaScript (if (elemento)) para evitar errores cuando ciertos elementos no existen en todas las páginas.

🏁 IMPLEMENTACIÓN DEL TABLERO

Semana 1-2 Implementación

Tablero con CSS Grid: estructura 6x6 adaptada

Decisión

Implementar el tablero principal usando CSS Grid con estructura de 6 columnas × 6 filas. A diferencia del Monopoly clásico (40 casillas grandes), el tablero se diseñó más compacto, permitiendo que encaje en una pantalla de escritorio sin necesidad de scroll.

Estructura del tablero

Las cuatro esquinas del tablero albergan los accesos principales: Salida/Inicio (superior izquierda), Parada Libre/Equipo (superior derecha), Váyase a la Cárcel/Contacto (inferior derecha), De Visita en la Cárcel/Bitácora (inferior izquierda). Las casillas laterales contienen referencias a tecnologías de desarrollo: HTML5, CSS3, GitHub, Vercel, JavaScript, entre otros. El centro del tablero aloja las fichas de jugadores, cartas de suerte/arca comunal y el botón de interactividad.

Desafío encontrado

Aplicar correctamente la propiedad grid-area con la sintaxis fila-inicio / columna-inicio / fila-fin / columna-fin para posicionar cada casilla sin superposiciones.

Resolución

Se utilizaron herramientas de desarrollo del navegador (Chrome DevTools) para visualizar el grid overlay. Se creó una clase CSS por cada posición (ej: .col-2, .fila2-col1). Se agregaron casillas incrementalmente, testeando después de cada cambio para verificar posicionamiento correcto.

Semana 2 Implementación

Sistema de navegación dual: tablero + menú tradicional

Decisión

Implementar dos sistemas de navegación simultáneamente: navegación a través del tablero (fichas clickeables, casillas interactivas) y menú de navegación tradicional (links en el header).

Justificación

Cumple con el requisito de la consigna de navegación fluida sin depender del botón atrás del navegador. Permite que usuarios exploren el sitio de forma lúdica a través del tablero, pero también ofrece acceso directo a través de menú convencional para quienes lo prefieran.

Desafío identificado

Asegurar que ambos sistemas de navegación funcionen de forma consistente sin conflictos. Posicionar las fichas de forma visible y accesible en el centro del tablero.

Resolución

Las fichas se implementan como elementos <a> con estilos circulares (border-radius: 50%), posicionadas en una sección central del grid. El menú superior mantiene la estructura de navegación estándar con hover effects. Ambos sistemas se probaron en múltiples navegadores para garantizar funcionamiento consistente.

Semana 2 Implementación

Modal de contacto: implementación del formulario de comunicación

Decisión

Implementar un modal emergente para contacto, con estética temática ("Declaración Policial" coherente con Monopoly). El modal se abre al hacer clic en el enlace "Contacto" del menú o en la casilla "Váyase a la Cárcel" del tablero.

Justificación

Mantiene coherencia temática. Un modal es más eficiente que navegar a una página separada de contacto. Permite al usuario comunicarse sin abandonar el flujo principal del sitio.

Desafío resuelto

Hacer que el modal se abriera y cerrara correctamente sin efectos secundarios. Los botones presentaban comportamientos inesperados en diferentes contextos de la página.

Resolución

Se agregaron validaciones en JavaScript antes de adjuntar event listeners: if (elemento). Esto evita errores cuando el elemento no existe en cierta página (el modal de contacto existe en index.html pero no en perfiles). El modal utiliza classList.toggle() para mostrar/ocultar, y se puede cerrar haciendo clic fuera del modal o en el botón de cerrar (✖).

🎴 PERFILES INDIVIDUALES

Semana 2 Implementación

Tarjetas de perfil con efecto 3D flip (CSS transforms)

Decisión

Cada tarjeta de perfil posee dos caras: frente (datos personales y habilidades, representadas como "rentas") y reverso (películas y discos favoritos). Al hacer clic, la tarjeta rota 180 grados sobre su eje Y para mostrar la otra cara.

Justificación

El efecto simula las tarjetas de Monopoly físicas. Es visualmente atractivo e intuitivo. Permite presentar información adicional sin saturar el espacio. Cumple con el requisito de interactividad JavaScript en cada perfil.

Desafío técnico

Implementar correctamente CSS 3D transforms: perspective, transform-style: preserve-3d, rotateY(180deg). Los textos en el reverso aparecían invertidos/ilegibles. Necesario entender backface-visibility.

Resolución

Se aplicó backface-visibility: hidden a ambas caras de la tarjeta para ocultar la cara posterior cuando no es visible. Se estableció transform: rotateY(180deg) exclusivamente en el reverso mediante CSS. JavaScript maneja el giro agregando/removiendo la clase .girada al hacer clic en la tarjeta.

Semana 2 Implementación

Avatares generados con herramientas de IA y datos personales

Decisión

Utilizar herramientas de IA para generar avatares de los integrantes. Inicialmente, cada perfil muestra un ícono temático (ficha de juego: perro, sombrero, auto, dedal). Al hacer clic en el botón "Revelar Jugador", se reemplaza el ícono por el avatar generado con IA.

Justificación

Proporciona privacidad opcional: los usuarios pueden elegir si desean ver el avatar completo o mantener la temática de fichas. Aprovecha herramientas de IA para contenido visual, como permite la consigna. Permite documentación clara del proceso en el README.

Desafíos encontrados

Algunos avatares generados presentaban fondos cuadriculados de transparencia. Además, se requería completar información personal de cada integrante (datos base, habilidades, películas favoritas, discos favoritos). En algunos casos, datos iniciales eran placeholders temporales que necesitaban actualización.

Resolución

Para fondos cuadriculados: se recomendó usar herramientas de procesamiento de imágenes (ej: remove.bg) para limpiar fondos. Para datos incompletos: se estableció que cada integrante es responsable de proporcionar y revisar su información personal antes de la entrega final. Se agregó un sistema de mapeo en JavaScript (diccionario mapaJugadores) que asocia iconos con avatares para facilitar el toggle.

Semana 2 Implementación

Funcionalidad de toggle: Revelar/Ocultar Jugador

Decisión

Implementar un botón que permite intercambiar la imagen mostrada entre la ficha de juego (ícono) y el avatar real del integrante.

Justificación

Proporciona interactividad adicional en cada perfil, más allá del flip de tarjeta. Cumple explícitamente con el requisito de "una función dinámica propia en cada página de perfil".

Desafío técnico

Mapear correctamente cada ícono con su avatar correspondiente. Si el usuario alterna múltiples veces (revelar → ocultar → revelar), el sistema debe volver al ícono original sin generar errores.

Resolución

Se implementó un sistema de diccionarios en JavaScript: mapaJugadores (ícono → avatar) y mapaInverso (avatar → ícono), generado automáticamente. Al hacer clic en el botón, el código extrae el nombre del archivo actual usando split(), consulta el diccionario apropiado, reemplaza la imagen y actualiza el texto del botón entre "Revelar Jugador" y "Ocultar Jugador".

⚙️ ARQUITECTURA Y DECISIONES FINALES

Semana 2 Decisión

Centralización de CSS y JavaScript: un único archivo por tipo

Decisión

Todo el código CSS se centraliza en un único archivo style.css. Todo el código JavaScript se centraliza en un único archivo script.js. No se crean archivos separados por componente, sección o página.

Justificación

Respeta la estructura de carpetas requerida por la consigna (CSS en carpeta css/, JavaScript en carpeta js/). Un archivo centralizado es más fácil de mantener, debuggear y revisar. Evita complejidad innecesaria de imports/exports en un proyecto de esta escala.

Desafío identificado

Mantener código organizado y legible dentro de un único archivo sin que se vuelva caótico o difícil de navegar.

Resolución

Se organizan las secciones CSS con comentarios numerados (1. Reset, 2. Menú, 3. Contenedor, ..., 12. Bitácora) acompañados de separadores visuales claros. Cada sección agrupa estilos relacionados. Lo mismo en JavaScript: comentarios numerados diferenciando funcionalidades (1. Contacto, 2. Tarjetas, 3. Bitácora). Se mantiene indentación consistente y se evita código duplicado.

Semana 2 Proceso

Merge de ramas: consolidación del trabajo colaborativo en main

Decisión

Consolidar todas las ramas de trabajo independientes (perfil-brian, perfil-flavia, perfil-pedro, perfil-ludmila, rama de bitácora) hacia la rama principal main.

Justificación

Integración de trabajo para generar un sitio funcional completo. Permite verificar que todas las piezas funcionan correctamente juntas antes de publicación.

Desafío resuelto

Conflictos potenciales en Git entre ramas. Necesidad de revisar cambios antes de ejecutar merges. Algunos integrantes presentaban complejidad en la gestión de versiones.

Resolución

Un integrante con mayor experiencia en control de versiones se encargó de revisar cada rama antes de hacer merge. Se agregaron validaciones en JavaScript para evitar errores cuando ciertos elementos (como el modal de contacto) no existen en todas las páginas. Se revisó que index.html no presentara conflictos antes de cada merge.

Modal de contacto con formulario temático. Bitácora de desarrollo. Estructura de archivos organizada. Estilos coherentes con temática Monopoly.

  • Verificación de funcionalidad en múltiples navegadores
  • Completar README con documentación completa
